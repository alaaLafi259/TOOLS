# نظام إدارة عدة المواقع (Tools Inventory System)

نظام لتتبع عدة المواقع (كهيلتي وغيرها) بالكمية لكل صنف، عبر مخزن مركزي وعدة مواقع عمل، مع تقارير تكلفة شهرية/مجمعة/لكل موقع.

## 1. إنشاء مشروع Firebase

1. اذهب إلى https://console.firebase.google.com وأنشئ مشروع جديد (مثلاً: `tools-inventory`).
2. من القائمة الجانبية: **Build → Authentication** → فعّل **Email/Password**.
3. من القائمة الجانبية: **Build → Firestore Database** → أنشئ قاعدة بيانات (اختر وضع Production).
4. من **Project Settings → General → Your apps** → أضف تطبيق ويب (Web app)، وانسخ بيانات `firebaseConfig`.
5. الصق البيانات في ملف `js/firebase-config.js` بدل القيم الوهمية.

## 2. تفعيل قواعد الأمان (Firestore Rules)

من **Firestore Database → Rules**، الصق محتوى ملف `firestore.rules` الموجود في هذا المشروع، ثم اضغط Publish.

## 3. إنشاء أول حساب أدمن (مشرف عام)

1. من **Authentication → Users → Add user**، أنشئ حساب بريد وكلمة مرور لنفسك.
2. انسخ الـ **UID** الخاص بالحساب.
3. من **Firestore Database**، أنشئ يدويًا مستند في كولكشن `users`:
   - Document ID = الـ UID اللي نسخته
   - الحقول: `role: "admin"`, `name: "اسمك"`

بعد كده تقدر تسجل دخول من `index.html` بنفس البريد وكلمة المرور، وهيوديك مباشرة للوحة الأدمن.

## 4. إضافة مشرفي المواقع

لكل مشرف موقع:
1. من **Authentication → Users → Add user**، أنشئ له حساب بريد وكلمة مرور، وانسخ UID الخاص به.
2. من لوحة الأدمن → تبويب "المواقع" → أضف الموقع، والصق UID المشرف في الحقل المخصص.
   (النظام هيسجله تلقائيًا في كولكشن `users` بدور `supervisor` ومربوط بالموقع)

## 5. تشغيل النظام محليًا

النظام عبارة عن ملفات HTML/JS/CSS ثابتة (Static)، تقدر تفتحه بأي سيرفر بسيط:

```bash
npx serve .
# أو
python3 -m http.server 8080
```

## 6. رفعه على GitHub Pages

```bash
git init
git add .
git commit -m "أول نسخة من نظام إدارة عدة المواقع"
git branch -M main
git remote add origin <رابط الريبو بتاعك على GitHub>

```

بعدها من إعدادات الريبو على GitHub: **Settings → Pages** → اختر Branch: `main` → Save.
الموقع هيبقى متاح على رابط زي: `https://<username>.github.io/<repo-name>/`

## حالة العدة (تعمل / تالفة / تحت الصيانة / معطلة)

كل رصيد (بالمخزن أو بأي موقع) مقسّم لأربع حالات بدل رقم واحد. عند الصرف/الإرجاع/التحويل/الإتلاف تختار الحالة اللي تتعامل معاها. وفي حركة إضافية اسمها **"تغيير حالة"** لنقل كمية من حالة لأخرى في نفس المكان (مثلاً: قطعة كانت شغالة اتعطلت، أو رجعت من الصيانة سليمة) بدون ما تتحرك من مكانها. تبويب "التقارير" فيه ملخص إجمالي لكل حالة على مستوى الشركة، وجدول تفصيلي لكل صنف في كل مكان.

## المنطق الأساسي

- **الصنف (Category)**: له كود واحد (مثال `HLT-01`)، ورصيد إجمالي بالمخزن المركزي، ومتوسط تكلفة مرجّح يتحدث تلقائيًا مع كل عملية شراء.
- **الموقع (Site)**: له رصيد مستقل لكل صنف، محفوظ في `sites/{siteId}/stock/{categoryCode}`.
- **الحركة (Transaction)**: كل عملية (شراء، رصيد افتتاحي، صرف، إرجاع، تحويل، إتلاف) تُسجَّل في كولكشن `transactions` وتُحدّث الأرصدة تلقائيًا عبر `Firestore Transaction` (لضمان عدم تعارض الأرصدة).
- **التقارير**: تُحسب من بيانات `categories` و`transactions` مباشرة، بدون الحاجة لتخزين إضافي.

## ملاحظة مهمة عن الأمان

قواعد `firestore.rules` تسمح لأي مستخدم مسجل دخول (أدمن أو مشرف) بتعديل رصيد أي موقع، لأن التحقق الكامل من التحويلات المباشرة بين موقعين معقد جدًا في قواعد Firestore. الحماية الفعلية من "مين يقدر يعمل إيه" مطبقة في واجهة التطبيق (كل مشرف يشوف موقعه فقط). هذا مقبول لأنه نظام داخلي لموظفين موثوقين. لو احتجت لاحقًا حماية أقوى (تمنع تلاعب مشرف موقع بموقع تاني عن طريق أدوات المطور)، الحل هو الانتقال لـ Cloud Functions تنفذ الحركات بدل الكتابة المباشرة من المتصفح.
